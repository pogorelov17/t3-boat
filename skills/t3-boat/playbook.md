## Role playbook

The owner chose the agent-playbook role workflow for this machine, so every project follows its roles. Read the role table and the model rules below. Both come from the agent-playbook model set named by the profile; `reviewer1` and `reviewer2` are the playbook's two reviewer instances. Use the table even if the task mentions no model. Start each worker with `boat-worker start ROLE`, naming its row in the table. Every worker has a role here: `boat-worker start` without a role is refused, so do not start or brief generic workers.

1. Use the scout for code discovery with file/line evidence, and the researcher for external questions with primary source links and dates. For tests alone the executor checks out the requested revision, runs the tests and reports the commands, SHA and results.
2. Give the executor the Git URL, requirements, target branch and findings. For a new project, implement the smallest agreed feature and add a runnable acceptance check. If an existing project has no test suite, report that and use a check appropriate to the change. The executor uses the verified VM checkout, creates a task branch, changes code, tests, commits, pushes and opens a **Draft PR**.
3. Start reviewer1 and reviewer2 on separate fresh VMs. Give both the same requirements, base, PR URL and exact head SHA. Each independently checks out and verifies that SHA and reviews the entire change (requirements, architecture, correctness, edge cases, regressions, compatibility, security and test coverage). Require evidence, commands, test outcomes and one verdict, APPROVE or REQUEST_CHANGES. Keep their findings separate until both respond.
4. When both reviewers have answered, decide on arbitration before any repair, so the reviewed SHA stays unchanged. Start the arbiter on a fresh VM when the verdicts conflict, when the executor disputes a finding with evidence, or after two failed repair rounds. It reproduces each disputed claim on that SHA and cannot waive either approval. Take an UNRESOLVED ruling, or one that needs the owner's decision, to the owner with options and a recommendation before anything else.
5. If a blocking finding stands, run a fresh executor on the same PR branch, then two fresh reviewers on the new SHA. Give both reviewers the arbiter's ruling for any finding it overturned. If the arbiter overturned every finding behind a REQUEST_CHANGES and no ruling requires a change, start one fresh reviewer for that row on the unchanged SHA with only that ruling attached; its verdict replaces the disputed one. An approval of an older SHA does not carry over.
6. The change is ready when every acceptance criterion has evidence on the head SHA and both reviewers approve that same SHA. Verify the PR head has not moved. Report the final PR and both verdicts to the owner, who decides when to merge.

### Model history

Record the actual model ID for every executor, including repair rounds, in the parent chat. A model's identity is its provider plus family, for example Codex Sol for `gpt-6.2-sol`; effort does not make two models different. Before delegating a review or an arbiter ruling, resolve the selected model against worker capabilities and compare its provider and family with every model that authored changes on this PR. Apply the model rules below. An exception applies only when they name it, and only as they state it. Name it when you report the reviews. Give every reviewer the PR and requirements for an independent, read-only review on its own fresh VM.

If a model identity is uncertain or violates these rules, stop and request a different model. Check again if a provider reports a different model during the run and discard a verdict that violates these rules. Keep both reviewers read-only.

For an Astra role configured at high effort, the pilot supports a reported escalation to xhigh for trading or money calculations, authentication, concurrency, migrations, infrastructure, compatibility, large cross-module refactors, conflicting reviews or repeated failure. Verify support first and announce the reason before launch. Keep explicitly customized settings for other roles and never choose max automatically.

In the parent updates, add the reviewed SHA and both verdicts once they exist.
