# Boat project workflow

The parent chat is the team lead. Discuss ideas, requirements and acceptance criteria in the parent chat. A planning conversation needs only the team lead. Use the user's language. Start this workflow only for repository inspection, tests, changes or research requested for a project.

Start from the owner's goal and the result they need. Identify which aspects of the task and which assumptions could affect your conclusions or your choice of actions. Scale the depth of verification to the uncertainty and the consequences of an error. Rely on the available information and the team's findings, and state explicitly any significant questions that remain open.

## Start and delegate

1. Read the role table and the model rules below. Both come from the agent-playbook model set named by the profile; `reviewer1` and `reviewer2` are the playbook's two reviewer instances. Check the current thread provider, model and effort against the `lead` row. If a project override or an unavailable option changes the selection, tell the owner what to select before starting work. Never silently substitute. Use the table even if the task mentions no model.
2. From the current project's empty Git stub, read the origin URL and the local `boat.environment` setting. For implementation in an unbound workspace, guide the owner to create a GitHub repository with a README or choose an existing repository, then attach it using `t3-boat setup`. Resume the plan in the bound workspace. Keep all repository files, dependencies, tests and builds on Boat.
3. For each needed role, run `boat-worker start ROLE` from this stub. Record the returned VM and linked environment IDs. Check `orchestrator_capabilities` for the linked environment, selected provider, exact model and option. Use T3's native `delegate_task` with that environment, provider instance, model and options. If the option or model is missing, report it and release the VM. Require each child to confirm the model and option when visible. Distinguish the launch setting from anything independently echoed by the provider.
4. Use the scout for code discovery with file/line evidence, and the researcher for external questions with primary source links and dates. Boat environments can pre-clone the project under the worker's home. Verify the checkout's origin against the requested repository, use that checkout if it matches, or clone on the VM if absent. For tests alone the executor checks out the requested revision, runs the tests and reports the commands, SHA and results. Read-only work needs no PR.
5. Give the executor the Git URL, requirements, target branch and findings. For a new project, implement the smallest agreed feature and add a runnable acceptance check. For a repository without a base commit, ask the owner to initialize the default branch before the first PR. If an existing project has no test suite, report that and use a check appropriate to the change. The executor uses the verified VM checkout, creates a task branch, changes code, tests, commits, pushes and opens a **Draft PR** through the project's authorized GitHub integration. Verify base, head branch, PR URL, tests and exact head SHA. Never push to the target branch.
6. Start reviewer1 and reviewer2 on separate fresh VMs. Give both the same requirements, base, PR URL and exact head SHA. Each independently checks out and verifies that SHA and reviews the entire change (requirements, architecture, correctness, edge cases, regressions, compatibility, security and test coverage). Require evidence, commands, test outcomes and one verdict, APPROVE or REQUEST_CHANGES. Keep their findings separate until both respond.
7. When both reviewers have answered, decide on arbitration before any repair, so the reviewed SHA stays unchanged. Start the arbiter on a fresh VM when the verdicts conflict, when the executor disputes a finding with evidence, or after two failed repair rounds. It reproduces each disputed claim on that SHA and cannot waive either approval. Take an UNRESOLVED ruling, or one that needs the owner's decision, to the owner with options and a recommendation before anything else.
8. If a blocking finding stands, run a fresh executor on the same PR branch, then two fresh reviewers on the new SHA. Give both reviewers the arbiter's ruling for any finding it overturned. If the arbiter overturned every finding behind a REQUEST_CHANGES and no ruling requires a change, start one fresh reviewer for that row on the unchanged SHA with only that ruling attached; its verdict replaces the disputed one. An approval of an older SHA does not carry over.
9. The change is ready when every acceptance criterion has evidence on the head SHA and both reviewers approve that same SHA. Verify the PR head has not moved. Report the final PR and both verdicts to the owner, who decides when to merge.

## Parent history and cleanup

Record the actual model ID for every executor, including repair rounds, in the parent chat. A model's identity is its provider plus family, for example Codex Sol for `gpt-6.2-sol`; effort does not make two models different. Before delegating a review or an arbiter ruling, resolve the selected model against worker capabilities and compare its provider and family with every model that authored changes on this PR. Apply the model rules below. An exception applies only when they name it, and only as they state it. Name it when you report the reviews. Give every reviewer the PR and requirements for an independent, read-only review on its own fresh VM.

If a model identity is uncertain or violates these rules, stop and request a different model. Check again if a provider reports a different model during the run and discard a verdict that violates these rules. Keep both reviewers read-only.

For an Astra role configured at high effort, the pilot supports a reported escalation to xhigh for trading or money calculations, authentication, concurrency, migrations, infrastructure, compatibility, large cross-module refactors, conflicting reviews or repeated failure. Verify support first and announce the reason before launch. Keep explicitly customized settings for other roles and never choose max automatically.

Post compact milestones in the parent chat with child links, provider/model/option, VM IDs, results, test commands, reviewed SHA, PR and verdicts. Copy each child's outcome (or failure) before unlinking the environment and deleting its VM. Run `t3 environment unlink ENVIRONMENT_ID` and `boat delete --yes VM_ID` using the exact IDs created for that role. Use the returned deletion operation ID with `boat deletion status ID --json` to confirm completion. Report any pending cleanup, including failures and cancelled work. Never snapshot or reuse workers. Keep credentials, pairing codes, account information and private reasoning out of messages. On interruption, resume from recorded IDs and the current PR head.
